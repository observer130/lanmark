## 1. 目标与非目标

### 目标

1. **自动同步循环**（桌面客户端）：周期 / 保存后 / 前台恢复 / 上线恢复自动回合；开关联动（默认开），关闭时手动「立即同步」仍可用
2. **删除传播**（tombstone）：一端删除 → 另一端软删，铁律安全（内容未变才静默传播；删后编辑过则按 LWW 裁决）
3. **LWW 冲突裁决**：两端离线改同一文件 → **mtime 较新者自动留原路径**，较旧者自动保留为可见冲突副本（`<stem>-冲突<时间>`，在目录树里），用户无需任何操作
4. **多端收敛**：修复双客户端基线缺陷（§5 步骤 8），服务器侧 push 同步做 mtime 仲裁（§5.1），桌面×2 + 手机×1 无人值守收敛
5. **同步状态 UI**：在线状态、最近同步时间、合并报告（哪版赢、输家副本在哪）

## 3. 协议演进（v1 → v1.1，全部加法式、向后兼容）

| 变更 | 内容 | 兼容性 |
|---|---|---|
| 新端点 `GET /api/v1/tombstones` | 需鉴权；返回 `[{path, hash, mtimeMs, deletedAt}]` | 旧服务器 404 → 客户端按空列表处理，删除传播静默关闭（退化 M2 行为，不报错） |
| `PushResult` + `serverHash: Option<String>` | 该路径在服务器上**操作后的最终 hash**：干净落盘 = 所推 hash；被仲裁降级 = 原路径现有 hash | 新增字段，旧客户端忽略 |

| `/info`、`/manifest`、`/pull` 不变 | — | — |

## 4. LWW 裁决规则（M3 的核心语义）

### 4.1 元组比较

版本元组 = `(mtime_ms, size, hash_hex)`，字典序，**大者赢**：

- mtime 不同 → mtime 新者赢（正常路径）
- mtime 相同（同毫秒，跨设备罕见）→ size 大者赢
- size 相同 → hash 字典序大者赢（hash 相同则内容相同，本不会进裁决）
- 删除参与裁决时，删除的元组取 `(tombstone.mtime_ms, 0, tombstone.hash)`——size 记 0，故 **mtime 平手时编辑恒赢删除**（偏保守，保数据在树里）

### 4.2 三种分歧的裁决

| 分歧 | 裁决 | 输家去向 |
|---|---|---|
| **edit/edit**（两端都改了同一文件，均 ≠ 基线） | mtime 新者留原路径 | 较旧者 → 冲突副本 `<stem>-冲突<mmdd-HHMM>[N]<ext>`（复用 M2 `write_conflict_copy`，进索引，随下回合同步到全端） |
| **edit/delete**（一端 tombstone，另一端有内容且 hash ≠ tombstone hash） | 按 §4.1 元组比较（删除元组 size=0） | 编辑赢 → 文件在删除侧复活；删除赢 → 文件入删除侧回收站（内容可找回） |
| **删除传播**（tombstone 与现存文件 hash 相同 = 删后没再改） | 不裁决，直接传播 | 双方回收站都有 |

**铁律核查**：所有分支输家内容都落盘（冲突副本 / 回收站），无静默丢失；静默动作（hash 相同的删除传播）不丢任何内容。

### 4.3 时钟偏移

mtime 依赖设备时钟。个人局域网设备通常 NTP 同步，偏移秒级以下；即使偏移导致「裁决方向反了」，输家仍留副本，**无数据丢失**，用户可在副本里找回。可接受，文档钉住。

## 5. 回合语义 v2（客户端）

编号沿用 docs/05 §8b（M2 回合）：

0. 本地 reindex（不变，磁盘为事实源）
1. 拉 manifest + **tombstones（新）** + 本地清单 + 基线
2. 四分类（不变：仅服务器有→拉 / 仅本地有→推 / hash 同→跳 / hash 异→三方对比）
3. **（新）服务器 tombstone 处理**：hash 同 → 本地软删 + 记本地 tombstone（`report.deleted++`）；hash 异 → 按 §4.2 edit/delete 裁决（编辑赢 → push 本地 P 复活，服务器按 D4 清 tombstone；删除赢 → 本地软删 + tombstone）；本地无 P → 补记 tombstone 跳过
4. **（新）本地 tombstone vs 服务器 manifest**：镜像 §5 步骤 3（方向对调；删除赢 → 调 `/delete`）
5. **edit/edit 冲突（LWW 裁决，取代 M2「本地恒赢」）**：
   - 本地 mtime 新 → M2 既有行为：服务器版本拉为本地冲突副本，本地 P 以 baseHash=服务器现 hash 推送（服务器侧 §5.1 仲裁保证干净落地）
   - **服务器 mtime 新（M2 没有的方向）→ 先把本地当前字节存为冲突副本，再 pull 服务器 P 覆写本地**（副本命名幂等：失败重跑产生 `-2`，不丢不重）
   - 平手 → §4.1 元组；两个客户端各自独立裁决可能方向相反 → 服务器仲裁 + 基线修复保证 **≤2 个回合收敛**（无丢失）
   - 每个裁决产生一个 `MergeEvent`
6. 拉取（不变，批量 32；**pull 成功的路径清除本地对应 tombstone**，D4）
7. 推送（不变，批量 8；**服务器对干净落盘/仲裁获胜的路径清除对应 tombstone**，D4）
8. **基线（G3 修复）**：= 回合开始时的 manifest，按本回合结果更新——拉取路径 → 实拉 hash；推送路径 → **`serverHash`**（被仲裁降级时 = 原路径 hash）。堵住多端缺陷：M2 在「push 被服务器改名」后仍把自己 hash 写进基线，下一轮误判「只有服务器改过」→ 快进拉取覆盖本地版本（内容仅存于副本）
9. 持久化：tombstones（TTL 清理）+ 基线 + 报告

### 5.1 服务器侧 push 仲裁（新增）

服务器处理 push、`baseHash` 与现状不符（竞态：另一客户端刚改过）时，不再无条件把来件冲突改名，改为按 §4.1 元组与**当前 P** 比较：

- 来件元组更大 → 来件赢：当前 P 存为服务器侧冲突副本（`write_conflict_copy`），来件落 P
- 来件元组更小/平手 → 来件冲突改名（M2 既有行为），当前 P 保留

`serverHash` 始终返回操作后 P 的最终 hash。此规则让「推送到达顺序 ≠ 保存时间顺序」的竞态也收敛到正确的 LWW 结果，且避免旧版赢 + 下回合再翻案产生的冗余副本。

**序列化前提不变**：服务器 runtime 单线程、handler 天然串行，仲裁的检查-落盘无竞态（M2 既有前提）。

## 6. 可发现性（替代人工解析的设计）

- **副本在树里**：冲突副本是普通笔记（进索引、可搜索、可打开、参与同步）——用户一眼可见「有个旧版本」，想合并就手动合并后删副本，不管它就静静躺着
- **合并报告**：`SyncReport.conflicts` → `Vec<MergeEvent>`，SyncSection 展示「自动合并 N 项（较新留原名）」+ 逐条「`工作/笔记.md` → 副本 `…-冲突0920-1030.md`（保留 10:30 版）」，点击副本路径打开对应笔记
- **删除传播**：`report.deleted` 计数 + 列表，文案「已同步删除 N（进回收站）」
- 手机端（服务器面板）：库中冲突副本计数（扫描 `冲突` 命名笔记）+ 最近回合时间；手机端无客户端循环，裁决只发生在客户端回合中，服务器侧仲裁的副本同样进树可见

## 7. 自动同步循环（TS 驱动；仅客户端——手机是服务器，无循环）

### 设置

- `syncAuto: bool`（默认 **true**）：`app_config_dir/config.json` 的 `AppConfig` 加字段（serde default true，旧配置兼容）
- 开关在桌面客户端面板（SyncSection）；关闭 = 停止定时器/探测/自动回合，仅保留手动「立即同步」
- 文案注明：桌面应用完全关闭后无后台同步（app 模型，非常驻；手机侧才是常驻中心）

### 触发器（开关开时）

| # | 触发 | 回合时机 |
|---|---|---|
| A | 周期探测：对每个已配对服务器 `GET /info`（无鉴权轻量），在线状态 60s 至多 1 回合 | 在线且距上回合 ≥60s → 回合 |
| B | 离线退避：探测失败 → 该服务器下轮探测间隔 1s→2s→4s→…→60s 封顶；离线→在线跳变 | 跳变时立即回合 |
| C | 保存完成：vault store 保存成功后经轻量 `CustomEvent` 通知（避免两 store 循环依赖），5s 内无新保存 | 5s 后（尾沿纪律，与 M2 P0「不打字中途同步」一致）——**这是「商用无冲突感」的主要来源：在线时分歧窗口从小时级压到秒级** |
| D | 应用回前台（visibilitychange / focus） | 立即探测 + 回合门控 |
| E | 手动「立即同步」 | 立即（恒可用，不受开关限制） |

- 所有触发走同一入口：尊重 `syncing` 串行锁；C/E 保留 M2「同步前 flush 脏编辑」
- vault 未打开（unconfigured）→ 循环空转
- mDNS 连续监听（P2）：连续探测失败 3 次后 browse 一次，发现同名服务器则更新 profile url 并触发回合；不实现则手输重配对兜底

### 探测实现

Rust 新增命令 `sync_probe(serverId) -> {online, name, notes, assets}`（GET /info，3s 超时）；TS 循环状态机 per-server 记录 `{lastProbeAt, failCount, online, lastRoundAt}`。

## 10. 验收标准（M3）

1. **三端收敛**：桌面×2 + 手机×1 各自改动（含附件），自动循环（不点任何按钮）≤3 个回合三端一致
2. **离线自动同步**：飞行模式 → 改 3 篇 → 恢复网络 → ≤2 个探测周期内自动同步，三端互见
3. **LWW 裁决**：双端离线改同一篇（保存时间不同）→ 同步 → 较新版在两端原路径、较旧版为可见冲突副本（内容完整），**全程无人工操作**；报告列出合并明细；次回合收敛（副本三端互见）
4. **删除传播**：桌面删一篇 → 同步 → 手机与桌面 2 该笔记均消失（三端回收站均有）；随后从回收站恢复并编辑 → 同步 → 按 LWW 裁决（编辑时间 vs 删除时间），无手动决策
5. **开关**：关自动同步 → 5 分钟内无回合（日志观测），手动按钮有效；再开 → ≤60s 恢复回合
6. **服务器恢复**：杀手机 App 进程（FGS 重启、自动开库复活）→ 桌面探测退避、≤60s 内恢复并自动完成一轮
7. `pnpm test` + `cargo test` 全绿；CI 三端绿；真机走查（REDMI K90 / Android 16）

## 12. 已知限制与风险

- 桌面 mDNS 多播不可达（docs/05 §8h）：发现仍靠手输 URL；探测循环不依赖 mDNS，不受影响
- 60s 周期回合以 reindex 开头：M1 护栏 500 笔记 ≈22ms，外推 1e4 笔记 ≈0.5s，可接受；未来量大改 mtime 预检（P2，不阻塞 M3）
